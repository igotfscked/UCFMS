# UCFMS claims files: field layouts

Status: **draft for Jake's review**, 2026-10-14. Companion to [APP_DESIGN.md](APP_DESIGN.md) section 4. Generated by `claims_layout.py` in this folder, which also writes the COBOL copybooks in [copybooks/](copybooks/); edit the field lists there and rerun it.

All fields are DISPLAY (no packed or binary), so records read cleanly with IDCAMS `PRINT CHARACTER`. Dates are `YYYYMMDD`, zeros when not set. Amounts are implied cents, like the tape's DollarAmount.

## How the files fit together

```
CLAIM.HDR  0000001234  JSMITH   O 0000001234  opened 20261014 ...  claimant ...
   |  CLAIM.ITEM keys, read in order with one generic browse on the claim ID:
   +-- 0000001234 0001  -> owner key SMITH...1740123456712019CK13000014
   +-- 0000001234 0002  -> owner key SMITH...1750987654302018AC01000203
   +-- 0000001234 0003  -> owner key SMITH...1750987654302018AC02000077 (removed)
CLAIM.AUDIT  every create / add / remove / submit / close / cancel, in time order
UCF.CTL      CLAIMNO record hands out the next claim ID
```

**The "linked list" of properties.** Jake described each claim's properties as a linked list. In a KSDS that chain is the key itself: claim ID + a 4-digit sequence number. A browse that starts at `0000001234 0000` and reads forward until the claim ID changes returns the claim's properties in the order they were added. No next/previous pointers are stored, so nothing can break when an item is removed: a removed item keeps its place with status `R`, and `CH-NEXT-ITEM-SEQ` in the header gives the next number. Up to 9,999 items per claim.

**Claims by user, by status.** An alternate index on the header, not a separate lookup file. Its key is user ID + status + claim ID, three fields placed next to each other at the front of the header for this purpose. Because the AIX is in the header's upgrade set, VSAM keeps it right automatically whenever a claim changes status, inside the same CICS unit of work; a lookup KSDS would need the program to delete and re-add its record on every status change. Each key is unique, so no AIX record grows large. A browse on the user ID alone lists that user's claims grouped O, S, C, X; on user + `O` it lists only their open claims. A second index on status + claim ID gives the same view across all users.

"User" here is the user who opened the claim. If claims get handed between staff, an `ASSIGNED-TO` field with its own index can be added later.

**Not stored on purpose:** SSN, TIN, date of birth or bank details for the claimant. Identity proof goes to the Comptroller with the claim; keeping it here would make these files sensitive.

**Seed record.** Each claims file is created with one blank record whose claim ID is 0, so the empty KSDS can be opened (JCL job UCFCLDEF). Programs and browses skip claim ID 0; real IDs start at 1.

## Datasets and indexes

| Dataset | Organisation | Key | Record length |
|---|---|---|---|
| `HLQ.CLAIM.HDR` | KSDS, one record per claim | CH-CLAIM-ID (bytes 1-10) | 700 |
| `HLQ.CLAIM.ITEM` | KSDS, one record per property on a claim | CI-CLAIM-ID + CI-ITEM-SEQ (bytes 1-14) | 246 |
| `HLQ.CLAIM.AUDIT` | ESDS, append only, one record per change | none (read in time order; batch sorts by claim) | 210 |
| `HLQ.UCF.CTL` | KSDS, a few named records | CT-REC-ID (bytes 1-8) | 100 |

| Alternate index | Over | Key fields | Offset | Length | Type | Answers |
|---|---|---|---:|---:|---|---|
| `HLQ.CLAIM.HDR.BYUSER` | `HLQ.CLAIM.HDR` | CREATED-BY + STATUS + CLAIM-ID-2 | 10 | 19 | UNIQUEKEY | My claims, by status: generic key user (8) or user + status (9) |
| `HLQ.CLAIM.HDR.BYSTAT` | `HLQ.CLAIM.HDR` | STATUS + CLAIM-ID-2 | 18 | 11 | UNIQUEKEY | All claims in one status, oldest ID first (reports, work queues) |
| `HLQ.CLAIM.ITEM.BYPROP` | `HLQ.CLAIM.ITEM` | OWNER-KEY | 14 | 66 | NONUNIQUEKEY | Which claims include this property |

Offsets are 0-based as IDCAMS `KEYS(length offset)` wants them; the tables below use 1-based columns.

## Status codes and dates

| STATUS | Meaning | Date field set | Items editable |
|---|---|---|---|
| `O` | OPEN | DATE-OPENED | yes |
| `S` | SUBMITTED | DATE-SUBMITTED | no |
| `C` | CLOSED | DATE-CLOSED | no |
| `X` | CANCELED | DATE-CANCELED | no |

Every status change also sets STATUS-DATE, LAST-UPD-*, adds 1 to VERSION, and writes an audit record, all in one unit of work. The BYUSER and BYSTAT indexes follow the change automatically.
